## 2. Архитектурные решения (ADR)

### ADR-001: Haskell как основной язык

**Контекст:** Проект переписывается с C++ на язык, обеспечивающий формальную верификацию и безопасность типов.

**Решение:** Haskell 2010 с GHC 9.6.5.

**Обоснование:**
- Сильная статическая типизация исключает целые классы ошибок (null pointer, type confusion)
- Система эффектов (IO, STM, ReaderT) делает сайд-эффекты явными
- LiquidHaskell позволяет доказывать инварианты (налоги >= 0, дебет = кредит)
- Однопроходная сборка мусора упрощает конкурентность
- Компиляция в статический бинарник упрощает деплой

**Последствия:**
- Жёсткие требования к типовой безопасности
- Необходимость Haskell-разработчиков для поддержки
- Нативная интеграция с PostgreSQL через Persistent/Esqueleto

### ADR-002: Stack vs Cabal

**Контекст:** Выбор системы сборки для Haskell-проекта.

**Решение:** Stack с resolver lts-22.21 (GHC 9.6.5).

**Обоснование:**
- Воспроизводимые сборки (lock-файлы resolver)
- Изолированный GHC (не требует системного)
- Удобное управление зависимостями
- Интеграция с Hackage и Stackage

**Последствия:**
- `stack.yaml` как единый источник истины для версий
- `extra-deps` для пакетов вне Stackage (ekg, cryptonite, jose)

### ADR-003: PostgreSQL как единое хранилище

**Контекст:** Выбор базы данных для ERP-системы.

**Решение:** PostgreSQL 16 как основная БД + Redis для кэша и очередей.

**Обоснование:**
- ACID-транзакции критичны для финансовых операций
- Мощные оконные функции для расчёта себестоимости (FIFO)
- JSONB для гибких схем (классификаторы, метаданные)
- Расширяемость (триггеры, хранимые процедуры, LISTEN/NOTIFY)
- Event Sourcing через `jsonb` и `BIGSERIAL` для порядка событий

**Последствия:**
- Тяжёлые вычисления вынесены в хранимые процедуры (calc_vat, calc_bill_totals)
- Триггеры для аудита и консистентности
- Partitioning для таблиц событий

### ADR-004: Servant для REST API

**Контекст:** Выбор веб-фреймворка.

**Решение:** Servant с генерацией типизированных API.

**Обоснование:**
- Типобезопасные эндпоинты — компилятор проверяет маршруты
- Автоматическая генерация клиентов и swagger-спецификации
- Middleware-композиция через типы
- Интеграция с Aeson для JSON

**Последствия:**
- API определён на уровне типов (Server.hs)
- Swagger-документация (planned via servant-swagger)
- Middleware chain: Metrics → RateLimiter → Correlation → Tenant → Auth → RBAC

### ADR-005: Event Sourcing + CQRS

**Контекст:** Архитектурный паттерн для ключевых доменов (склад, бухгалтерия).

**Решение:** Event Sourcing с CQRS для Inventory и Accounting доменов.

**Обоснование:**
- Полная аудит-трасса всех изменений
- Возможность восстановить состояние на любую дату
- FIFO-расчёт себестоимости через проекции событий
- Разделение команд и запросов оптимизирует производительность

**Статус:** Реализовано для Inventory (списание по FIFO через LotEntity), Accounting (журнал проводок). EventStore — реальный PostgreSQL-бэкенд (262 строки).

**Детали:** См. `docs/architecture/EVENT_SOURCING.md`.

### ADR-006: Persistent + Esqueleto для ORM

**Контекст:** Доступ к базе данных из Haskell.

**Решение:** Persistent (шаблонная генерация схемы) + Esqueleto (типобезопасные JOIN).

**Обоснование:**
- Template Haskell-генерация типов из схемы
- Esqueleto даёт типобезопасные SQL-запросы
- Raw SQL для сложных процедур (FIFO, себестоимость)

**Последствия:**
- Модели данных в `DAL/Schema.hs` (43 сущности)
- Типы в `DAL/Types.hs` с экземплярами FromJSON/ToJSON
- Конверсия entity→domain тип в `DAL/Conversion.hs`

### ADR-007: JWT для аутентификации

**Контекст:** Механизм аутентификации для REST API.

**Решение:** JWT (JSON Web Tokens) с библиотекой jose.

**Обоснование:**
- Stateless — не требуется серверная сессия
- Поддержка tenant_id в claims для мультиарендности
- Стандартный протокол, поддержка во всех клиентах

**Реализация:** `src/Surypus/JWT/` — генерация и верификация токенов.

### ADR-008: Vanilla JS (без фреймворка) для веб-клиента

**Контекст:** Выбор фронтенд-технологии.

**Решение:** Vanilla JavaScript без внешних фреймворков.

**Обоснование:**
- Минимальные зависимости
- Прямой контроль над DOM и UX
- API-клиент через Axios для HTTP
- localStorage для JWT и tenant context

**Последствия:**
- Один файл `web/index.html` (~2778 строк)
- Модуль `web/js/api.js` для API-методов
- Нет необходимости в npm/webpack

## 3. Предметная область (DDD — Domain-Driven Design)

### Домены и универсальный язык

| Домен (Bounded Context) | Ядро | Агрегаты | События |
|------------------------|------|----------|---------|
| **Inventory (Склад)** | Товары, остатки, партии, склады | Goods, Lot, Stock | GoodsReceived, GoodsShipped, LotCreated |
| **Accounting (Бухгалтерия)** | План счетов, проводки, обороты | AccPlan, LedgerEntry | EntryPosted, BalanceChanged |
| **Sales/Purchases (Закупки/Продажи)** | Счета, заказы, клиенты | Bill, Order, Person | BillPosted, OrderFulfilled |
| **Tax (Налоги)** | Ставки, расчёты, отчётность | TaxRate, TaxReport | — |
| **Payroll (Зарплата)** | Сотрудники, начисления, выплаты | Employee, Salary | SalaryPaid |
| **CRM** | Сделки, контакты, компании | Deal, Contact, Company | DealWon, DealLost |
| **Production (Производство)** | Техкарты, заказы, MRP | TechCard, WorkOrder | ProductionCompleted |
| **Reports (Отчёты)** | Шаблоны, генерация, экспорт | ReportTemplate | ReportGenerated |
| **MultiTenancy** | Организации, пользователи | Tenant, User | TenantCreated |

### Ключевые бизнес-правила (Инварианты)

```haskell
── Налог: результат >= 0 и <= цена
calcVAT amount rate = amount * (rate / 100.0)
── свойство: 0 <= calcVAT amount rate <= amount

── Бухгалтерия: Σ Дебет = Σ Кредит
── для каждой проводки: sum debits == sum credits

── Склад: Остаток = Начальный + Приход - Расход
── для каждой позиции: Stock.qtty >= 0

── FIFO: списание по себестоимости первых по времени партий
── Lot.rest >= 0 для каждой партии
```

### Ограничения (Constraint) в БД

```sql
-- CHECK constraint на уровне БД
ALTER TABLE stock ADD CONSTRAINT stock_qtty_nonneg CHECK (qtty >= 0);
ALTER TABLE lots ADD CONSTRAINT lots_rest_nonneg CHECK (rest >= 0);
ALTER TABLE acc_entry ADD CONSTRAINT acc_entry_balanced
  CHECK ((SELECT SUM(debit) = SUM(credit) FROM acc_entry WHERE doc_id = NEW.doc_id));
```

### Middleware Chain (порядок применения)

1. **MetricsMiddleware** — сбор метрик (ekg)
2. **RateLimiter** — ограничение запросов
3. **Correlation** — correlation ID для трассировки
4. **Tenant** — определение текущего tenant
5. **Auth (JWT)** — проверка токена
6. **RBAC Authorization** — проверка прав доступа
7. **Handler** — бизнес-логика

## 6. Ключевые нефункциональные требования

| Требование | Реализация |
|-----------|------------|
| **Консистентность** | ACID-транзакции PostgreSQL, CHECK constraints, триггеры |
| **Аудит** | Event Store — append-only лог всех изменений |
| **Мультиарендность** | TenantId в JWT claims, изоляция на уровне запросов |
| **Производительность** | Redis-кэш, пагинация, оконные функции |
| **Безопасность** | JWT + RBAC (30+ прав, 4 роли) |
| **Отказоустойчивость** | Docker Compose, health checks, dumb-init |
| **Наблюдаемость** | ekg (метрики), correlation ID, логирование |
