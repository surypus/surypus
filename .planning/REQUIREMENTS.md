# Requirements: Surypus ERP

**Defined:** 2026-10-23
**Core Value:** Пользователь может провести реальную хозяйственную операцию — принять товар, выставить счёт, оплатить его и увидеть корректные проводки и остаток — на работающем сервере с настоящей базой данных.

## v1 Requirements

Требования первого рабочего среза. Каждое отображается в фазу roadmap.

### Bootstrap & Schema Truth (BOOT)

- [ ] **BOOT-01**: Сервер запускается: `app/Main.hs` читает конфигурацию из env, собирает пул соединений и поднимает Warp на настраиваемом порту
- [ ] **BOOT-02**: `GET /api/v1/health` возвращает 200 и отражает реальное состояние БД, а не константу
- [ ] **BOOT-03**: Миграции применяются одним каноническим runner'ом с checksum-леджером и advisory lock; повторный запуск идемпотентен
- [ ] **BOOT-04**: Дублирующиеся префиксы миграций разрешены, сборка схемы с нуля на пустой БД проходит; существующие V001/V256-конфликты `bills`/`accounts`/`payments` закрыты forward-миграцией
- [ ] **BOOT-05**: CI поднимает реальный PostgreSQL, применяет миграции и гоняет `stack test` — без `pendingWith` на ключевых тестах
- [ ] **BOOT-06**: Один тулчейн (GHC 9.6.5 / LTS 22.21) во всех конфигурациях: `stack.yaml`, `cabal.project`, Dockerfile, devcontainer, CI

### Money & VAT Canon (MONEY)

- [ ] **MONEY-01**: В домене ровно один тип денег (`Money` поверх `Data.Decimal`, масштаб 2); сканирующий тест падает, если `Double` появляется в денежной подписи
- [ ] **MONEY-02**: Одна политика округления (half-up) с тестами на граничные значения
- [ ] **MONEY-03**: Ставки представлены типами `RatePercent` и `RateFraction` с закрытыми конструкторами и единственной точкой преобразования
- [ ] **MONEY-04**: Смешение единиц ставки невозможно скомпилировать; налоговая функция принимает только типизированную ставку
- [ ] **MONEY-05**: Оба импоста `Decimal`-типов и все дублирующиеся VAT-движки удалены из кода и `exposed-modules`

### Ledger Canon & Transaction Gateway (LEDGER)

- [ ] **LEDGER-01**: `Finance.Ledger` — единственный модуль проводок; несбалансированную транзакцию невозможно сконструировать (умный конструктор, а не проверка после факта)
- [ ] **LEDGER-02**: База данных отклоняет несбалансированный коммит через deferred constraint trigger — обойти инвариант из кода нельзя
- [ ] **LEDGER-03**: `App.Tx.runWrite` — единственный путь записи; арендатор (tenant) устанавливается transaction-local и не течёт между запросами
- [ ] **LEDGER-04**: Каждая хозяйственная операция пишется одной транзакцией: документ + позиции + проводки + движения склада либо коммитятся вместе, либо не коммитятся вовсе
- [ ] **LEDGER-05**: Повторное проведение с тем же idempotency key не создаёт дубль проводок
- [ ] **LEDGER-06**: Инвариант Σ дебет = Σ кредит проверен property-тестами на генераторах и доказан refinement-аннотациями (LiquidHaskell или эквивалент)
- [ ] **LEDGER-07**: Отчёт «обороты и сальдо по счёту» и пробный баланс за период строятся из таблиц проводок

### Master Data (MAST)

- [ ] **MAST-01**: Пользователь ведёт справочник товаров: код/SKU, наименование, единица измерения, категория, ставка НДС по умолчанию, цена продажи, признак активности
- [ ] **MAST-02**: Пользователь ведёт контрагентов с типом «поставщик» / «покупатель» / «оба»
- [ ] **MAST-03**: Заведён один склад; остатки ключуются парой (товар, склад), а не только товаром
- [ ] **MAST-04**: Используемые в документах товары и контрагенты деактивируются, а не удаляются; жёсткое удаление блокируется

### Inventory (STCK)

- [ ] **STCK-01**: Пользователь оформляет и проводит документ прихода с позициями (товар, количество, цена)
- [ ] **STCK-02**: Журнал движений склада append-only: `RECEIPT` / `ISSUE` / `ADJUSTMENT`, со ссылкой на документ-источник и временем
- [ ] **STCK-03**: Остаток выводится из движений; кэш остатка допустим только как пересобираемая проекция
- [ ] **STCK-04**: Проведение счёта создаёт движение `ISSUE` и пару проводок «себестоимость / товары» в той же транзакции
- [ ] **STCK-05**: Проведение с отрицательным остатком блокируется с ошибкой, указывающей товар, склад, запрошенное и доступное количество
- [ ] **STCK-06**: Себестоимость ведётся по средневзвешенной; приход пересчитывает среднюю, списание считает себестоимость по ней

### Invoicing & Posting (BILL)

- [ ] **BILL-01**: Пользователь создаёт счёт с позициями; по каждой позиции считаются нетто, НДС и брутто, по документу — итоги
- [ ] **BILL-02**: Номер счёта уникален в пределах типа документа и года и генерируется внутри транзакции БД (sequence/`UPDATE ... RETURNING`), не через `max(number)+1` в Haskell
- [ ] **BILL-03**: Счёт живёт по циклу draft → posted; редактируется только черновик, проведённый счёт неизменяем
- [ ] **BILL-04**: Проведение применяет правила: приход `Дт Товары / Кт КЗ`; счёт `Дт ДЗ / Кт Выручка + Кт НДС` плюс `Дт Себестоимость / Кт Товары`; оплата `Дт Касса / Кт ДЗ`
- [ ] **BILL-05**: Назначение счетов берётся из карты системных ролей счетов, а не из захардкоженных ID
- [ ] **BILL-06**: Засеян плоский план счетов с картой ролей; его можно пересоздать без поломки правил проводок

### Payments (PAY)

- [ ] **PAY-01**: Пользователь регистрирует оплату по счёту, включая частичную
- [ ] **PAY-02**: Оплата создаёт проводку и обновляет состояние счёта (частично оплачен / оплачен)

### Auth & RBAC (AUTH)

- [ ] **AUTH-01**: Пользователь входит и выходит через серверную сессию; сессия переживает перезагрузку страницы
- [ ] **AUTH-02**: Пароли хранятся как Argon2id-хеши и перехешируются при успешном входе; путь с несолёным SHA-256 удалён
- [ ] **AUTH-03**: Действуют три роли — `admin`, `accountant`, `storekeeper`; авторизация default-deny
- [ ] **AUTH-04**: Тест перечисления маршрутов падает, если какой-либо маршрут (включая `/ui/*`) не классифицирован как public или protected
- [ ] **AUTH-05**: Администратор создаёт пользователей и назначает роли
- [ ] **AUTH-06**: UI-формы защищены CSRF-токеном, привязанным к сессии
- [ ] **AUTH-07**: Ни одна проверка прав не возвращает безусловный `True`; репозиторий прав читает реальные данные

### Server-rendered UI (UI)

- [ ] **UI-01**: Экран товаров: список, создание, редактирование, деактивация
- [ ] **UI-02**: Экран склада: список приходов, создание и проведение прихода, история движений по товару
- [ ] **UI-03**: Экран счетов: создание счёта с позициями и проведение
- [ ] **UI-04**: Экран оплаты и просмотра проводок и пробного баланса
- [ ] **UI-05**: HTMX-фрагменты возвращают частичную разметку и корректный 422 с сообщениями валидации; страницы не кэшируются

### Verification & Quality Gates (VERF)

- [ ] **VERF-01**: `stack test` зелёный, `DAL.EventStoreSpec` подключён в `other-modules`, coverage gate не скрывает ошибки парсинга
- [ ] **VERF-02**: Smoke-скрипт проходит весь сквозной путь на реальном PostgreSQL и падает при расхождении остатка или баланса
- [ ] **VERF-03**: В `src/` не остаётся «тихих» заглушек: каждый stub либо удалён, либо падает с `error "not implemented"`, либо реализован
- [ ] **VERF-04**: Проверка баланса проводки входит в блокирующий CI-гейт; при её отключении сборка падает

## v2 Requirements

Отложено до следующей версии; в текущий roadmap не входит.

### Documents

- **DOCS-01**: Сторно и reversal проведённых документов
- **DOCS-02**: Кредит-ноты и возвраты от покупателя
- **DOCS-03**: Документ ручной корректировки склада

### Payments

- **PAY2-01**: Исходящие платежи поставщикам (закрытие КЗ)
- **PAY2-02**: Взаимозачёт и привязка одного платежа к нескольким счетам

### Accounting

- **ACCT-01**: Входящие остатки при миграции из другой системы
- **ACCT-02**: Создание и архивирование счетов (только листовых)
- **ACCT-03**: Закрытие периода и блокировка дат

### Operations

- **OPS-01**: Просмотр аудит-лога
- **OPS-02**: Экспорт пробного баланса и журнала в CSV
- **OPS-03**: Разделение landing-страниц по ролям
- **OPS-04**: Единый канон очереди задач — `DAL.Queue` на PostgreSQL, DDL вынесен в миграцию

## Out of Scope

| Feature | Reason |
|---------|--------|
| Зарплата и кадры | Не нужны для доказательства работоспособности основного контура |
| Мульти-склад и перемещения | Только при появлении второй физической локации |
| FIFO / партии / серийные номера / сроки годности | Требует точности учёта, которой в v1 не требуется |
| Мультивалютность и курсы | Нет внешних контрагентов в v1 |
| Заказы поставщикам и 3-way match | Закупки без согласования в v1 |
| Банковская сверка и импорт выписок | Объём операций не оправдывает |
| Кастомные роли и права на уровне полей | Достаточно трёх фиксированных ролей |
| PDF/Excel отчёты и дашборды | После того как бухгалтерии можно доверять |
| GraphQL-шим, WebSocket, Kafka/EventBridge | Вторичные интеграции; сначала HTTP + БД |
| Redis-очереди и in-memory job runner | Заменяются одним каноном `DAL.Queue` на PostgreSQL |
| Мобильный клиент и не-Haskell UI | Ограничение языка проекта (AGENTS.md) |
| OAuth / LDAP / внешние IdP | В v1 только локальные пользователи и роли |
| Прайс-листы и конвертация единиц измерения | Одна цена и простая единица на товар |
