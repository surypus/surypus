\chapter{Role-Based Access Control (RBAC)
System}\label{role-based-access-control-rbac-system}

\section{Overview}\label{overview}

Surypus implements a comprehensive Role-Based Access Control (RBAC)
system to manage user permissions across the API. This document outlines
the role hierarchy, permissions, and how they are applied to API
endpoints.

\section{Role Hierarchy}\label{role-hierarchy}

The system defines four primary roles with different permission levels:

\subsection{\texorpdfstring{1. \textbf{Admin
(RoleAdmin)}}{1. Admin (RoleAdmin)}}\label{admin-roleadmin}

\begin{itemize}
\tightlist
\item
  \textbf{Description}: Full system access
\item
  \textbf{Permissions}: All permissions
\item
  \textbf{Typical Users}: System administrators, developers
\item
  \textbf{Key Permissions}: AdminAccess, all CRUD operations
\end{itemize}

\subsection{\texorpdfstring{2. \textbf{Manager
(RoleManager)}}{2. Manager (RoleManager)}}\label{manager-rolemanager}

\begin{itemize}
\tightlist
\item
  \textbf{Description}: Business operations management
\item
  \textbf{Permissions}: Most write operations, all read operations
\item
  \textbf{Typical Users}: Department managers, supervisors
\item
  \textbf{Limited By}: Cannot access admin functions, cannot delete
  sensitive data
\end{itemize}

\subsection{\texorpdfstring{3. \textbf{User
(RoleUser)}}{3. User (RoleUser)}}\label{user-roleuser}

\begin{itemize}
\tightlist
\item
  \textbf{Description}: Standard user with basic read and write access
\item
  \textbf{Permissions}: Limited write operations, basic read operations
\item
  \textbf{Typical Users}: Regular employees, data entry staff
\item
  \textbf{Limited By}: Read-only for sensitive areas (accounting,
  payroll), no delete permissions
\end{itemize}

\subsection{\texorpdfstring{4. \textbf{Viewer
(RoleViewer)}}{4. Viewer (RoleViewer)}}\label{viewer-roleviewer}

\begin{itemize}
\tightlist
\item
  \textbf{Description}: Read-only access for reporting and analysis
\item
  \textbf{Permissions}: Read-only across the system
\item
  \textbf{Typical Users}: External stakeholders, auditors, analysts
\item
  \textbf{Limited By}: Cannot perform any write or delete operations
\end{itemize}

DELETE /v1/rbac/grants/:from/:to/:permission?resource=... - AdminAccess
GET /v1/rbac/audit?principal=...&resource=...&offset=...&limit=... - AdminAccess
POST /v1/rbac/audit/cleanup?keep=...                     - AdminAccess
\end{verbatim}

Dynamic roles are stored as scoped permissions and can be restricted to
a canonical resource key such as \texttt{location:1}, \texttt{bill:42},
\texttt{report:sales}, or \texttt{accounting-entry:17}.

Delegation grants support temporary escalation through an expiry
timestamp. Expired grants can be cleaned up explicitly through the
cleanup endpoint. Updating a grant refreshes its expiry window while
keeping its principal and scoped permission key. Audit entries can be
paginated with \texttt{offset}/\texttt{limit} and trimmed with the audit
cleanup endpoint.

\section{Implementation Details}\label{implementation-details}

\subsection{Role-Permission Mapping}\label{role-permission-mapping}

The system uses a permission matrix where each role is associated with
specific permissions:

\begin{Shaded}
\begin{Highlighting}[]
\KeywordTok{data} \DataTypeTok{RolePermission} \OtherTok{=} \DataTypeTok{RolePermission}
\NormalTok{  \{}\OtherTok{ rpRole ::} \DataTypeTok{Role}
\NormalTok{  ,}\OtherTok{ rpPermissions ::}\NormalTok{ [}\DataTypeTok{Permission}\NormalTok{]}
\NormalTok{  \}}
\end{Highlighting}
\end{Shaded}

\subsection{Permission Checking}\label{permission-checking}

Permissions are checked using the \texttt{checkPermission} function:

\begin{Shaded}
\begin{Highlighting}[]
\OtherTok{checkPermission ::} \DataTypeTok{Text} \OtherTok{{-}\textgreater{}} \DataTypeTok{Permission} \OtherTok{{-}\textgreater{}} \DataTypeTok{Either} \DataTypeTok{String}\NormalTok{ ()}
\end{Highlighting}
\end{Shaded}

This function: 1. Takes a role (as Text) 2. Takes a required permission
3. Returns \texttt{Right\ ()} if the role has the permission 4. Returns
\texttt{Left\ error} if the role lacks the permission

\subsection{API Integration}\label{api-integration}

The \texttt{requirePermission} helper in \texttt{Surypus.API.Server}
provides access checking:

\begin{Shaded}
\begin{Highlighting}[]
\OtherTok{requirePermission ::} \DataTypeTok{Text} \OtherTok{{-}\textgreater{}} \DataTypeTok{Permission} \OtherTok{{-}\textgreater{}} \DataTypeTok{Handler}\NormalTok{ ()}
\end{Highlighting}
\end{Shaded}

This function returns a 403 Forbidden response if the permission check
fails.

The runtime request pipeline now also supports a request-aware
authorization resolver via advanced middleware. It can:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Authenticate non-public requests
\item
  Resolve required permission from the incoming request path/method
\item
  Load dynamic roles and delegation grants from an RBAC store
\item
  Apply resource-level checks using scoped permissions
\item
  Emit audit entries for allow/deny decisions
\end{enumerate}

\section{Security Considerations}\label{security-considerations}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Default Deny}: All permissions must be explicitly granted
\item
  \textbf{Role Validation}: Invalid roles default to the most
  restrictive (Viewer)
\item
  \textbf{Token-based Verification}: Permissions are verified from JWT
  tokens
\item
  \textbf{Permission Immutability}: Permissions are defined at compile
  time
\end{enumerate}

\section{Configuration}\label{configuration}

Role definitions are in \texttt{src/Surypus/RBAC.hs}. To modify
permissions:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Update the \texttt{Permission} datatype
\item
  Add the permission to relevant \texttt{RolePermission} entries
\item
  Update endpoint documentation
\item
  Add corresponding tests
\end{enumerate}
