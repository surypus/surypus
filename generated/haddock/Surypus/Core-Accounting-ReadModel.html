applyAccountCreated :: AccountReadModel -> Event -> AccountReadModel Source #

Apply AccountCreated event

The real producer (appendAccountingEvent) stores toJSON (AccountCreatedEvent ev) — a tagged union whose payload sits under "contents" with the record field names as keys (acCodeacNameacType/acParentId). The code and name are read from there (legacy flat payloads are still honoured); the previous version discarded them and always set Nothing, so a replayed model carried no account identity. The type is 'Maybe Text' because that is what the schema actually holds: account_type is a TEXT column (ASSETLIABILITY…) and the producer writes acType as the same Text category, so no id mapping is needed or invented. The field used to be Maybe Int and was always set to Nothing because no Int mapping existed anywhere in the codebase, which silently discarded the category on every replay. armCurrencyId stays Nothing for a different reason: the producer event has no currency field.

applyJournalEntryPosted :: AccountReadModel -> Event -> AccountReadModel Source #

Apply JournalEntryPosted event

The real producer (appendAccountingEvent) stores toJSON (JournalEntryPostedEvent ev) — a tagged union whose payload sits under "contents" with the record field names as keys (jepAmountjepDebitAccjepCreditAcc). The amount is read from there (legacy payloads carrying only a top-level "changeAmount" are still honoured), and the sign follows the double-entry side of this model's account: +amount on the debit side, -amount on the credit side, 0 for any other account — mirroring the pure replay layer applyEvent.

applyBalanceAdjusted :: AccountReadModel -> Event -> AccountReadModel Source #

Apply BalanceAdjusted event

No producer in the codebase writes a BalanceAdjusted variant yet (the AccountingEvent union has no such constructor), so this is the documented contract for a future writer:

  • changeAmount is applied RELATIVE to the current balance and drives the debit/credit totals (same sign convention as applyJournalEntryPosted).
  • newBalance, when present, overrides the current balance absolutely; when absent the balance keeps its old value plus changeAmount — a partial payload must never zero a live balance.
  • Both payload shapes are honoured through unwrappedFields (tagged-union as written by appendAccountingEvent and flat legacy objects), matching the other appliers.
